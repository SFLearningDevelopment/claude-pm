Step 1 of 5
The problem
Example 4 · Tier 1 Sprint planning Single-context 2–3 turn interaction

Sprint 3 planning for the Meridian AI Assistant is in two hours. Sarah has a high-level epic — "AI Query Assistant MVP" — that needs to be broken into properly sized, acceptance-criteria-ready user stories before the team can commit.

Epic — Meridian AI Assistant: AI Query Assistant MVP
Build an AI-powered query assistant for the Meridian client portal. Clients should be able to ask natural language questions about their accounts and get accurate, cited responses. The assistant must not answer questions outside the scope of Meridian's data. It should feel conversational but professional. Must work on mobile. Response time target: under 3 seconds. Integration with the existing portal authentication (already built in Sprint 2).
Team capacity — Sprint 3 (2 weeks)
Carlos (AI/ML lead): 10 days available
Priya (frontend lead): 8 days available (one FE engineer still at 80%)
Backend engineer (Rohan): 10 days available
QA (shared): 4 days available
Total capacity: ~32 story points (using 1pt ≈ 1 day, with 20% buffer for BAU)

The AI Assistant epic is deliberately vague at this stage — "feel conversational but professional" is not a testable acceptance criterion. Before the sprint planning session, Sarah needs stories with clear acceptance criteria, estimated sizes, and dependency flags so the team can have an informed commitment conversation.

Why this is PM work, not just developer work: Developers can decompose technically. PMs decompose for deliverability — which means understanding what can be demo'd to the client at the end of the sprint, what has external dependencies, and what needs to be excluded from Sprint 3 to avoid scope creep. Claude can help structure this thinking before the room fills up.

Step 2 of 5
The naive approach

The naive prompt produces stories without acceptance criteria, without sizing guidance, and without flagging what's actually achievable in a 2-week sprint:

Sarah (naive prompt)
Break this AI assistant epic into user stories. [pastes epic]
Naive output — unsized stories without acceptance criteria
1. As a client, I want to ask natural language questions about my account
2. As a client, I want to receive accurate responses to my questions
3. As a client, I want the assistant to cite its sources
4. As a client, I want the assistant to work on mobile
5. As a client, I want responses within 3 seconds
6. As a client, I want the assistant to stay within Meridian's data scope
7. As a client, I want a conversational experience
What's wrong: These are feature descriptions masquerading as user stories. None have acceptance criteria — how do you test "accurate responses"? How do you test "conversational experience"? There are no size estimates, no dependency flags, and no indication that stories 1, 2, 5, and 6 together represent significantly more than 32 story points of work for Sprint 3. The team would arrive at planning and spend 40 minutes discovering this.

Step 3 of 5
The Claude interaction

Sarah provides capacity context, a sizing convention, and asks Claude to flag what fits in the sprint and what should be deferred — with acceptance criteria for each story.

Sarah — Turn 1
I'm a senior PM at a cloud consultancy. I need to decompose this AI assistant epic into sprint-ready user stories for a 2-week sprint. Here are my constraints: Team capacity: ~32 story points total (1 point ≈ 1 day of work) Team: AI/ML engineer (10 days), frontend engineer (8 days), backend engineer (10 days), QA shared (4 days) Sprint goal: A demo-able AI query MVP that a client can actually use to ask account questions For each story, provide: — User story (As a... I want... So that...) — Acceptance criteria (3–5 testable conditions using Given/When/Then format) — Story point estimate — Which team member(s) own it — Any dependencies on other stories or external systems Also tell me: — What fits in Sprint 3 given the capacity — What should be deferred to Sprint 4 and why Epic: [pastes epic]
Claude — Turn 1
Sprint 3 Stories — Meridian AI Query Assistant MVP Story AI-01: RAG pipeline foundation As a system, the AI assistant must retrieve relevant account data from Meridian's data store to answer client queries accurately. Acceptance criteria: — Given a client query, the RAG pipeline retrieves the top 3 relevant document chunks from Meridian's indexed account data — Given a query outside Meridian's data scope, the pipeline returns no results and triggers the out-of-scope response — Given indexed data, retrieval completes in under 1 second (to support the 3s total response time) — Given a new document is added to the index, it is available for retrieval within 5 minutes Estimate: 8 points | Owner: Carlos (AI/ML) | Dependencies: Meridian data access + indexing pipeline (external dependency — confirm with Meridian IT) Story AI-02: Query interface — portal integration As a client, I want to type a natural language question in the portal so that I can get an answer without navigating menus. Acceptance criteria: — Given I am authenticated, a query input field is visible on the portal dashboard — Given I type a query and submit, a loading state is shown within 200ms — Given a response is returned, it is displayed with the source citation visible — Given I am on mobile, the query interface is fully functional at 375px viewport width — Given the session expires, I am prompted to re-authenticate before my query is submitted Estimate: 5 points | Owner: Priya (frontend) | Dependencies: AI-01 (API endpoint), portal auth (Sprint 2 — complete) Story AI-03: Out-of-scope guardrail As a client, when I ask a question outside Meridian's account data, I receive a clear and professional response explaining what the assistant can help with. Acceptance criteria: — Given a query that matches no Meridian data, the assistant responds with a predefined message explaining its scope — Given the out-of-scope response, it suggests 2–3 topics the assistant can help with — Given any query, the assistant never fabricates information (verified by QA test set of 20 adversarial queries) Estimate: 3 points | Owner: Carlos (AI/ML) | Dependencies: AI-01 Story AI-04: Response latency validation As a client, I want responses within 3 seconds so that the assistant feels responsive and usable. Acceptance criteria: — Given a standard query, end-to-end response time (query submission to response displayed) is under 3 seconds for 95th percentile — Given a complex query requiring multiple retrieval chunks, response time does not exceed 5 seconds — Given a response time exceeds 3 seconds, a "still working" indicator is shown after 2 seconds Estimate: 3 points | Owner: Carlos (AI/ML) + Rohan (backend) | Dependencies: AI-01, AI-02 Story AI-05: QA test suite — MVP As a QA engineer, I want a test suite for the AI assistant so that we can validate accuracy and guardrail behaviour before demo. Acceptance criteria: — 30-question test set covering: in-scope queries (15), out-of-scope queries (10), adversarial queries (5) — All in-scope queries return a response with a valid citation — All out-of-scope queries return the guardrail message — All adversarial queries return either the guardrail message or a correct in-scope response Estimate: 4 points | Owner: QA | Dependencies: AI-01, AI-02, AI-03 Total Sprint 3: 23 points — within 32pt capacity ✓ Remaining capacity (9 points): buffer for integration issues and carried items from Sprint 2 Deferred to Sprint 4: — Conversation history / multi-turn queries (requires session state management — 6pts) — Admin monitoring dashboard for query logs (8pts) — Fine-tuning on Meridian-specific terminology (requires training data collection first — 10pts) These are deferred because they are not required for a client-demo-able MVP and would consume the sprint buffer needed for integration risk.
What changed: Every story has testable acceptance criteria. The sprint total is calculated against capacity. External dependencies are flagged. The deferred items have reasons — not just "left for later." Sarah arrives at planning with a proposal, not a question.

Step 5 of 5
Watch out
1. Claude will underestimate AI/ML work
AI-01's initial estimate of 8 points was optimistic — Carlos caught this in planning because he knew the indexing pipeline complexity. Claude doesn't know your team's velocity on AI work specifically. Always validate AI/ML story estimates with the technical lead before committing.
2. Acceptance criteria for AI quality are hard to make testable
"Accurate responses" and "conversational tone" are not testable. Claude will attempt to operationalise these — but you need to validate whether the test cases it proposes actually measure what the client cares about. A 30-question test set is a starting point, not a guarantee of production quality.
3. Claude cannot see your team's existing sprint board
If there are carried stories, existing technical debt items, or team commitments Claude doesn't know about, the capacity calculation will be wrong. Always provide the full capacity picture — not just the headline number.
The prompting discipline that makes this work:
(1) Provide team capacity by person — not just total points. (2) State the sprint goal — what needs to be demo-able. (3) Ask explicitly for what should be deferred and why. (4) Ask for dependencies — both internal (story-to-story) and external (client/third-party). (5) Validate with your tech lead before the planning session, not during it.
