The problem
Example 12 · Tier 3Cloud costsAI workloadsExecutive communication

Month 4 of the Meridian engagement. The Meridian AI Assistant has been running in a staging environment for three weeks. Carlos has sent Sarah the AWS cost report. The numbers are higher than the original estimate — and the reasons are technical.

Mark Donovan has asked for a cost update before the next board meeting. He approved a $120K budget for the AI Assistant workstream. The current AWS spend trajectory is projecting $180K over the build period — $60K over budget. He needs to understand why, whether it is controllable, and what options exist.

Carlos's AWS cost data (raw)
Compute: EC2 p3.2xlarge instances for embedding generation — $4,200/month. Originally estimated on t3.large ($340/month) — underestimated GPU requirement for production-scale embedding workload. Storage: Pinecone vector store — $1,100/month (estimated $200/month — vector dimensions and index size 4× original estimate due to longer document chunks). API costs: OpenAI ada-002 embedding calls — $890/month at current indexing rate. Data transfer: $340/month (cross-AZ). Total current monthly burn: $6,530. Original monthly estimate: $2,400. Variance: +$4,130/month (+172%). Projected 18-month total at current rate: $117,540 compute + overhead = ~$180K. Optimisation options: (1) Switch to Graviton3-based instances for inference (saves ~35% on compute), (2) reduce embedding re-indexing frequency from daily to weekly (saves ~$400/month on API costs), (3) use AWS Bedrock Titan embeddings instead of OpenAI ada-002 (saves ~$600/month, quality TBC). Estimated savings if all three: ~$2,100/month — brings projection to ~$142K.
Why this is Tier 3: The PM must take Carlos's technical cost breakdown — which contains GPU instance types, vector store pricing, embedding API economics, and optimisation options — and turn it into a board-ready narrative that explains a $60K budget overrun without alarming the client, while being technically accurate and presenting concrete options. Translating cost overruns is harder than translating progress updates — the client is being asked to accept additional spend.

Step 2 of 5
The naive approach

The naive approach presents the raw numbers with a technical explanation — accurate but useless for a non-technical executive:

Sarah (naive — cost update to Mark)
Hi Mark — wanted to flag a budget update on the AI Assistant workstream. Current AWS spend is running at $6,530/month vs our estimate of $2,400/month. The main drivers are the GPU compute requirements for embedding generation (we needed p3.2xlarge instead of t3.large), the Pinecone vector store running larger than expected, and OpenAI API costs. We're looking at optimisations including switching to Graviton3 instances and Bedrock Titan embeddings. Projected total is now ~$180K vs the $120K approved budget. Happy to discuss.
What's wrong: Every sentence contains jargon Mark cannot decode. "p3.2xlarge," "Pinecone vector store," "Graviton3," "Bedrock Titan embeddings" — none of these mean anything to a financial services CTO without an AI background. The $60K overrun is presented as a number without context — is this normal for AI projects? Was the estimate naive from the start? What is Mark being asked to decide? "Happy to discuss" again defers the decision to a call that should not need to happen if the communication is done correctly.
3
Step 3 of 5
The Claude interaction

Sarah asks Claude to translate the cost data into a board-ready narrative with three components: why the overrun happened, whether it is reasonable, and what the options are — all without technical jargon.

Sarah — Turn 1
I'm a senior PM on an AI project for a financial services client. I need to explain a cloud cost overrun to a non-technical CTO (financial services background). The overrun is $60K over an approved $120K budget. Requirements: — No technical jargon (no GPU, EC2, Pinecone, Graviton, embeddings API — translate everything) — Explain why the estimate was wrong — honestly, not defensively — Explain whether this level of overrun is typical for AI projects at this stage — Present three options with cost implications — Tone: confident and direct, not apologetic. The overrun is real but manageable. — Format: short narrative + options table, max 250 words Raw cost data from my engineering lead: [pastes Carlos's data]
Claude — Turn 1
AI Assistant — Cloud Cost Update The AI Assistant's cloud infrastructure costs are running above the original estimate. Current monthly spend is $6,500 against an estimate of $2,400 — a variance of 170%. Over the 18-month build period, this projects to approximately $180K against the approved $120K. Why the estimate was higher than expected The original estimate was based on standard web application infrastructure costs. Once development began, it became clear that the AI Assistant requires specialised processing power to analyse and index Meridian's account documents at the speed needed for real-time client queries. This type of AI workload typically costs 3–5× more to run than a standard web application — a pattern seen consistently across the industry. The original estimate did not account for this, which is a scoping gap we should have caught earlier. Three options | Option | What changes | Projected total | Decision needed | |---|---|---|---| | A — Status quo | Nothing | ~$180K | Accept $60K additional | | B — Partial optimisation | Switch 2 of 3 cost drivers to lower-cost alternatives | ~$155K | Accept $35K additional | | C — Full optimisation | All three cost drivers optimised (some quality testing required) | ~$142K | Accept $22K additional; allow 2-week quality validation | Recommendation: Option B. The optimisations in Option C require quality validation that could delay the October investor day demonstration. Option B reduces the overrun significantly while protecting the delivery timeline.
Sarah — Turn 2
Add one sentence at the top that leads with the recommendation — Mark reads the first sentence and decides whether to read on.
Claude — Turn 2
Added opening sentence: "We recommend approving an additional $35K for the AI Assistant workstream — this resolves the infrastructure cost variance while protecting the October investor day timeline." [rest of narrative follows]
What changed: The $60K overrun is now contextualised as a known pattern in AI projects, not a project management failure. The options are presented with decision language — what Mark needs to approve, not what the engineering team needs to do. The recommendation leads, so Mark knows what he is being asked to decide before he reads the detail. No jargon. No deferral to a call.

✓ Sarah's addition — programme context
To provide full context: the $35K increase on the AI Assistant workstream represents a 2.5% increase on the total Meridian programme budget of $680K across all three workstreams. The Cloud Migration and Portal workstreams are currently tracking within budget. The overall programme financial position remains healthy.
Why this addition matters: Mark is the CTO of a financial services firm. He is used to thinking in programme-level numbers. A $35K variance on a $120K AI workstream sounds like a 29% overrun. A $35K variance on a $680K programme sounds like normal project variance. Claude produced the AI workstream narrative — Sarah added the programme context that reframes the number correctly. This is the PM's financial judgment layer.

Step 5 of 5
Watch out
1. Never present a cost overrun without a recommendation
Presenting options without a recommendation forces the client to make a technical decision they are not equipped to make. Always lead with your recommendation — the client can override it, but they should not have to derive it themselves. Claude will present options neutrally unless asked to recommend. Always ask.
2. Claude will contextualise optimistically
Claude stated that 3–5× cost overruns are "seen consistently across the industry" — which is broadly true for AI infrastructure, but Sarah should validate this claim with Carlos before presenting it to the client. If the client's CFO challenges it, Sarah needs a source, not Claude's general knowledge.
3. The options table needs decision language, not technical language
Claude's first draft used "switch 2 of 3 cost drivers" — still partially technical. Sarah revised to "what changes / projected total / decision needed" — framing each option as what Mark needs to approve, not what the engineering team needs to do. Always review option descriptions for residual jargon.
The discipline that makes this work:
Lead with the recommendation, not the problem. Contextualise the number at the right level (programme, not workstream). Translate options into decision language. Validate any industry benchmarks Claude uses before presenting to the client. The PM's financial judgment — knowing that $35K on $680K reads differently than $35K on $120K — cannot be delegated to Claude.
